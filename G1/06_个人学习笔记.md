# G1 个人学习笔记

## 1. UPPAAL 模型整体架构

UPPAAL 模型的核心是若干并行时间自动机模板及其进程实例。一个可检查模型通常包含：

1. 全局声明：常量、共享变量、时钟、通道、函数和类型。
2. 模板：局部声明、位置、初始位置和迁移边。
3. 位置：可带不变量，限制自动机在该位置最多停留多久。
4. 迁移：可带卫士、同步和更新；卫士决定何时允许发生，更新改变离散变量或复位时钟。
5. 系统声明：实例化模板并用 `system` 指定并行进程。
6. 查询：对组合系统的可达状态和路径进行检查。

### 1.1 时间约束的配合

位置不变量和迁移卫士必须共同设计。例如位置不变量为 `x <= 20`，若唯一出口卫士写成 `x > 20`，系统永远无法离开，会在边界产生死锁。常见正确组合是：

```text
位置不变量：x <= 20
出口卫士：  x >= 20
出口更新：  x = 0
```

时钟只随时间增长，不能像普通变量一样任意赋值；常用更新是复位为 0。若忘记复位，后续位置可能立刻违反不变量或跳过预期等待时间。

### 1.2 并行通信

模板可以通过共享变量或通道同步。共享变量简单，但多个进程同时读写时容易产生隐含耦合；握手通道要求发送 `a!` 与接收 `a?` 同步发生，适合表达原子事件。广播、urgent、committed 等机制会改变调度或时间推进，应有明确建模理由，不能只为“让查询通过”而添加。

### 1.3 当前 v1 的架构理解

G5 v1 使用：

- 全局 `phaseClock` 控制灯相位。
- 车辆局部 `arrivalClock` 和 `crossingClock` 控制到达、穿越时长。
- 共享 `signal` 公开灯色。
- 共享 `crossingOccupied` 阻止车辆仍在路口时绿灯切换。
- `phaseClock <= GREEN_DURATION - CROSSING_MAX` 保证车辆只在剩余绿灯时间不少于最大穿越时间时进入。

这个结构适合课程基础模型，但活性仍需单独分析：一条迁移“可执行”不代表所有路径一定选择它，因此存在完成路径不等于必然完成。

## 2. 安全、活性和时限属性

### 2.1 安全属性

安全属性回答“坏事是否永远不会发生”，通常写成 `A[] p`。本项目例子：

```text
A[] (VehicleProcess.Crossing imply signal == GREEN)
A[] not deadlock
```

第一条是业务安全不变量；第二条是全局结构性质。无死锁不等于车辆最终通过，也不等于所有需求都满足。

### 2.2 可达性

`E<> p` 回答“是否至少存在一条路径到达 p”。例如：

```text
E<> VehicleProcess.Done
```

它适合证明场景可实现并生成见证，但不能证明所有车辆或所有执行最终完成。

### 2.3 活性

活性属性回答“好事是否最终会发生”。例如：

```text
VehicleProcess.Waiting --> VehicleProcess.Done
```

若系统允许无限等待、重复绕行或非公平地忽略某条可执行边，活性可能失败。处理方式不是把查询改弱，而是判断：需求是否真的要求必然进展；若要求，模型应增加合理的紧迫、同步或调度约束，并检查是否引入新死锁。

### 2.4 时限属性

时限属性不仅要求“最终发生”，还要求在 T 时间内发生。本项目可在车辆进入 `Waiting` 时复位观察时钟，超过 `WAIT_BOUND` 且尚未通行时进入 `Timeout`，再检查：

```text
A[] not WaitObserver.Timeout
```

关键是明确起算事件、结束事件、上界是否包含端点，以及观察者不能反向限制系统。

## 3. 模型评估指标设计

一个 LLM 输出是否“成功”不能只看 XML 是否看起来完整。应分层测量：

| 层次 | 指标 | 原因 |
| --- | --- | --- |
| 输出层 | 完整率、截断率 | 判断 LLM 是否给出可提取材料 |
| 语法层 | XML 解析率、UPPAAL 编译率 | 区分通用 XML 与工具语言错误 |
| 结构层 | 位置/边/时钟/同步错误数 | 发现能编译但模型结构错误的情况 |
| 执行层 | 仿真可运行率 | 检查关键场景是否真实可走 |
| 验证层 | 查询可执行率、性质通过率 | 检查模型是否满足统一需求 |
| 成本层 | 修复时间、修改项数 | 衡量输出对人工工作的实际价值 |
| 追踪层 | Prompt/raw/repair/结果关联完整率 | 保证实验可复查 |

分母必须固定。若每组生成 5 个样本，即使某样本在 XML 阶段失败，也仍属于该组分母；后续阶段记 `N/A`，不能删除后重新生成。

错误数也需统一口径。同一个“时钟未复位”可能导致多个查询失败，应把根因计为一个 E5 错误，并在影响字段关联多个结果，避免重复夸大错误数量。

## 4. Prompt 对形式化输出的影响

### 4.1 基础 Prompt

自然语言任务留给模型较大自由度，能观察 LLM 的默认建模能力，但常见风险是：省略系统声明、混入伪代码、漏复位时钟、生成不存在的查询标识符。

### 4.2 知识增强 Prompt

明确模板、时钟、不变量、卫士、复位和 XML 转义，预计能减少语法与结构错误。但它也可能让模型生成表面完整、实际语义仍错误的复杂结构，所以不能跳过验证。

### 4.3 安全约束 Prompt

加入“穿越时必须绿灯”“剩余绿灯足够”“无死锁”等约束，预计能减少核心需求错误。同时，约束越多越可能产生互相冲突的不变量和卫士，因此仍要检查 E5/E6/E9 类型问题。

### 4.4 实验解释原则

- P2 表现更好，只能说明本任务和本模型条件下，增加知识/约束与结果相关。
- 不能用 5 个样本声称对所有 LLM 或所有实时系统普遍有效。
- 需要同时报告失败类型变化，而不只报告总通过率。
- 若三组模型版本、日期或采样设置不同，就必须把它列为混杂因素。
- Prompt 设计本身也是实验对象，修改后必须形成新版本，不能覆盖旧文本。

## 5. G1 实操检查要点

### 建模前

- 需求是否给出明确进程、状态、时限和不在范围内的功能。
- 每个时限是否有起点、终点、上下界和单位。
- “存在路径”和“所有路径”是否区分。

### 模型审查

- 每个模板是否有初始位置，关键状态是否可达。
- 每个有上界不变量的位置是否在边界有可执行出口。
- 时钟是否在正确事件复位，是否错误使用全局/局部作用域。
- 通道两端是否匹配，共享变量是否存在竞争或不一致表示。
- 查询引用的实例名、位置名、变量名是否真实存在。

### 结果解释

- 结果来自实际 UPPAAL 工具还是仅来自人工推测。
- SAT/UNSAT/ERROR 是否分开。
- 失败轨迹是否被保留并定位到需求和模型元素。
- 修复是否只针对单条查询“打补丁”，并破坏其他性质。
- 报告措辞是否准确使用“存在”“所有”“最终”“时限内”。

## 6. 学习结论

1. 形式化模型质量由需求、时间语义、并发语义和查询共同决定，XML 可导入只是最低门槛。
2. 安全性质通常比活性性质更容易写成状态不变量；活性必须面对无限拖延和调度选择。
3. 有界响应需要在模型中显式保存时间上下文，不能只把自然语言“within T”照搬成未经确认的查询语法。
4. 评估 LLM 应保存完整失败样本，并把原始生成质量与修复后模型质量分开。
5. G1 的主要价值是冻结边界和口径，让 G2-G8 的独立工作可以合并成可追溯、可复验的实验结论。
