# 版本管理与评审规范

## 1. 目标

模型版本必须同时说明来源、需求范围、验证状态和证据。版本号不是简单文件后缀；只有达到对应验收门槛的模型才能标记为 v1、v2 或 v3。

## 2. 版本定义

| 标识 | 定义 | 所有者 | 当前状态 |
| --- | --- | --- | --- |
| `raw/<sample-id>` | LLM 首次原始输出，禁止人工改写 | G2 | 待生成 |
| `repair/<sample-id>/rN` | 针对某 raw 样本的第 N 次人工/LLM 修复尝试 | G2/G5 | 待实验 |
| `v1` | 单灯单车正常场景基础模型，完成基础安全/可达验证 | G5 | 已有候选并有三条通过记录 |
| `v2` | 正常场景整合版，吸收 G3/G4 审查并完成 G7/G8 回归 | G5 主责，G3/G4/G7/G8 评审 | 待完成 |
| `v3` | 在通过验收的正常模型上增加卡死、超时和恢复/永久故障语义 | G6 主责，G5/G7/G8 评审 | 待完成 |

raw 和 repair 不占用正式模型版本号。不能把挑选出的 raw 文件直接重命名为 v2，而不保留来源和修复记录。

## 3. 建议命名

```text
traffic_light_v1.xml
traffic_light_v1.queries.q
traffic_light_v1.verify.txt

traffic_light_v2.xml
traffic_light_v2.queries.q
traffic_light_v2.verify.txt

traffic_light_v3_fault.xml
traffic_light_v3_fault.queries.q
traffic_light_v3_fault.verify.txt
```

LLM 样本使用 `P<组>-R<序号>`，例如 `P2-R03`。修复版使用 `P2-R03-repair-r1.xml`，不得覆盖 `P2-R03/model.xml`。

## 4. 版本演进规则

### 4.1 raw 到 repair

- raw 文件只允许机械提取代码围栏，不允许内容修改。
- 每个修复项关联错误编码、原始证据、修改人和耗时。
- LLM 二次修复与人工修复分开标记，不能合并成一次“人工修正”。

### 4.2 v1 到 v2

v2 不是强制增加功能，而是正常场景的受审整合版，必须：

- 关联至少一批真实 raw 样本的错误审查结论。
- 解决 G3/G4 标为 `BLOCKER` 或 `MAJOR` 的适用问题。
- 冻结 `WAIT_BOUND` 或明确将时限性质列为未决项。
- 运行 Q-S01、Q-S02、Q-R01、Q-R02、Q-L01、Q-L02 及适用的 Q-T 查询。
- 对所有失败性质保存反例或给出经评审的范围说明。

### 4.3 v2 到 v3

- 正常行为回归查询必须继续运行，不能只测试故障分支。
- 故障触发、检测阈值和恢复策略均有需求编号。
- 正常轨迹和故障轨迹分开保存。
- 对“存在恢复”和“必然恢复”使用不同查询并准确表述。

## 5. 分支和提交约定

- 每位成员在自己的分支和目录内工作；跨目录修改应在提交说明中点名受影响成员。
- 一个提交只处理一类可审查事项，例如“增加 P1 raw 样本”或“修复时钟复位”。
- 提交信息建议格式：`<成员>: <对象> <动作>`，例如 `G3: classify guard errors in P1 samples`。
- 不提交许可证密钥、个人令牌、本机绝对路径、临时日志或未脱敏截图。
- 合并前保留原作者提交，不通过复制粘贴抹去贡献来源。

## 6. 评审门槛

| 门槛 | 检查内容 | 必须证据 |
| --- | --- | --- |
| Gate A 可追溯 | Prompt、raw、修复版、模型版本能互相追踪 | 样本 ID、提交号、版本登记 |
| Gate B 可解析 | XML 良构并可由目标 UPPAAL 版本加载 | 工具输出/截图 |
| Gate C 可仿真 | 正常灯循环和车辆路径可复现 | 轨迹、截图或录屏说明 |
| Gate D 结构审查 | 模板、位置、边、时钟、复位和同步完成交叉审查 | G3/G4 评审记录 |
| Gate E 形式验证 | 必选查询全部执行，失败项有轨迹和结论 | queries、verify 输出 |
| Gate F 文档一致 | 参数、模型、查询、结果和报告表述一致 | 最终检查清单 |

任何一个 Gate 未完成时，版本状态只能是 `DRAFT` 或 `CANDIDATE`，不能标记 `ACCEPTED`。

## 7. 评审流程

1. 作者提交候选模型、变更摘要和自测结果。
2. G3 审结构/时钟，G4 审同步/共享状态，结论分别记录。
3. G7/G8 执行与该版本匹配的查询并保存工具输出。
4. 作者修复问题，使用新提交和新结果，不覆盖失败证据。
5. G1 检查需求追踪、版本登记、评审签字和报告措辞。
6. 全组评审决定 `REJECTED`、`CHANGES_REQUESTED` 或 `ACCEPTED`。

## 8. 变更控制

以下变更必须在 `templates/版本登记.csv` 中记录，并触发受影响查询回归：

- 灯周期、到达/穿越范围、等待上限、故障阈值。
- 模板或进程实例数量。
- urgent/committed 位置、广播/握手通道语义。
- 安全条件、占用状态、时钟复位位置。
- 查询公式、实例名映射或观察者模板。
- 实验使用的 LLM 模型/版本、Prompt 文本或生成参数。

仅调整 XML 图形坐标且不改变语义时，可标记为 `layout-only`，但仍应说明。

## 9. 版本完成定义

一个正式版本只有在以下材料同时存在时才算完成：模型 XML、匹配的查询文件、实际验证输出、模型说明、已关闭/已接受的评审记录、版本登记项，以及能够追溯到具体 Git 提交的状态。
