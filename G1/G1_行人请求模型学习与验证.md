# G1：行人请求式交通灯模型学习与验证

## 1. 这份工作为什么适合 G1

G5 已经完成“信号灯 + 车辆”的基础模型。本模型保留交通灯主题，但改为“行人按键请求 + 控制器协调”，重点体现 G1 的系统需求抽象和整体逻辑设计，不与 G5 完全重复。

你需要掌握的四个简单知识点：

1. 用位置和迁移表达完整业务流程。
2. 用时钟、不变量、卫士和复位表达时间要求。
3. 用 `walkStart`、`walkDone` 通道同步控制器和行人。
4. 用安全、可达、活性和时限查询验证不同类型的需求。

## 3. 系统逻辑

### 3.1 控制器流程

```text
CarGreen
  --收到行人请求且车辆绿灯至少 5 秒-->
CarYellow（2 秒）
  --> AllRedBeforeWalk（1 秒清空路口）
  --walkStart!-->
PedestrianGreen
  --walkDone?-->
AllRedAfterWalk（1 秒清空路口）
  --> CarGreen
```

如果没有行人请求，`CarGreen` 每 10 秒通过自环复位 `phaseClock`，继续保持车辆绿灯。这样系统不会因为“无人请求”而被迫进入行人阶段，也不会在绿灯时间上界死锁。

### 3.2 行人流程

```text
Approach（1 到 4 秒到达）
  --requestPending = true, waitClock = 0-->
Waiting
  --walkStart?-->
Crossing（3 到 4 秒）
  --walkDone!-->
Done
  --arrivalClock = 0-->
Approach
```

`walkStart!` 必须和 `walkStart?` 同时发生，保证控制器切换到行人绿灯时，行人也同时进入 Crossing。`walkDone!` 在 `Crossing → Done` 上，和控制器的 `walkDone?` 一起发生，行人完成后控制器才离开行人绿灯。`Done → Approach` 不占用通道，只把 `arrivalClock` 复位，行人可以再次到达并请求。

## 4. 为什么等待上界最终定为 13 秒

最初我按“第一次请求”推导的是 12 秒：

1. 行人最早在系统时间 1 秒时到达并发出请求。
2. 车辆绿灯允许持续到系统时间 10 秒，即最多再等 9 秒。
3. 黄灯持续 2 秒。
4. 行人绿灯前的全红清空持续 1 秒。

```text
(10 - 1) + 2 + 1 = 12 秒
```

但这个 12 秒只对“第一次请求”成立，属于乐观值。给 `Pedestrian` 加上 `Done → Approach` 的循环边（更新 `arrivalClock = 0`，让行人可以反复过街）之后，行人可以在**车辆绿灯刚开始**（`phaseClock ≈ 0`）时到达并请求，此时要等满整个绿灯 10 秒，再加黄灯 2 秒、全红 1 秒：

```text
10 + 2 + 1 = 13 秒
```

把 `WAIT_BOUND` 设为 12 再验证时，UPPAAL 直接给出反例（`Controller.CarYellow + PedestrianProcess.Waiting`，`waitClock ≈ 11~12` 一路涨到 13），说明 12 秒确实不成立。因此把常量改成：

```uppaal
const int WAIT_BOUND = 13;
```

这个“先推导、再用工具推翻、最后修正常量”的过程本身，就是形式化验证比手推更可靠的最好例子。

对应查询：

```text
A[] (PedestrianProcess.Waiting imply waitClock <= WAIT_BOUND)
```

## 5. 八条查询怎么解释

| 查询 | 类型 | 你在汇报时可以怎么说 |
| --- | --- | --- |
| `A[] not deadlock` | 安全/结构 | 所有可达状态都不存在死锁 |
| `Crossing imply signal == PED_GREEN` | 安全 | 行人穿越期间一定显示行人绿灯 |
| `pedestrianCrossing imply Controller.PedestrianGreen` | 安全 | 占用标志与控制器位置保持一致 |
| `not (Crossing && CarGreen)` | 互斥安全 | 行人穿越和车辆绿灯不会同时发生 |
| `E<> Done` | 可达性 | 至少有一条执行路径能完成通行 |
| `Waiting --> Done` | 活性 | 每次开始等待后最终都会完成通行 |
| `Waiting imply waitClock <= 13` | 时限 | 等待状态不会超过推导并修正后的 13 秒 |
| `A[] (PedestrianProcess.Crossing imply PedestrianProcess.crossingClock <= CROSSING_MAX)` | 时限 | 穿越状态最多持续 4 秒 |

注意：`E<> Done` 只表示“存在完成路径”；`Waiting --> Done` 才表达“每次等待最终都会完成”。这是本模型最值得讲清楚的量词区别。

## 8. 你可以完成的简单学习任务

### 任务 A：画出流程并解释同步

在汇报中画出两个模板，说明 `walkStart` 为什么保证行人绿灯和 Crossing 同时开始，`walkDone` 为什么保证行人离开后灯色才改变。

### 任务 B：手算等待上界

根据 `CAR_GREEN_MAX`、最早请求时间、黄灯和全红时间重新计算 `WAIT_BOUND`。修改任一参数后，先预测查询是否通过，再运行验证。

### 任务 C：观察一个反例

临时把查询中的 `WAIT_BOUND` 改成 11，不改模型，运行：

```text
A[] (PedestrianProcess.Waiting imply waitClock <= 11)
```

该性质应失败。查看反例中行人在车辆绿灯早期发出请求、一直等到绿灯上界的轨迹（这也是把 `WAIT_BOUND` 从 12 改成 13 的直接原因）。实验后把查询恢复为 13。

### 任务 D：理解存在性与必然性

分别解释 `E<> Done` 和 `Waiting --> Done`。前者只需要一条成功路径；后者要求每次等待都最终成功。保存两条查询的结果截图。
