# 系统需求与模型边界

## 1. 文档目的

本文是全组建模和验证的需求基线。任何 Prompt、UPPAAL 模型、查询或实验统计都应标注所对应的需求编号。参数或边界发生变化时，先更新版本登记和评审记录，不能只改 XML。

## 2. 研究对象

实验对象是一个教学用途的交通灯实时系统。基础场景抽象一条受控车道、一个信号灯控制器和一辆车，重点研究 LLM 能否生成语法有效、时间约束一致、可仿真且可验证的 UPPAAL 模型。

本实验验证的是抽象模型内部的一致性，不代表真实道路控制器已经达到工程安全认证要求。

## 3. 进程拆分

| 建模对象 | UPPAAL 表达 | 必选版本 | 职责与接口 |
| --- | --- | --- | --- |
| 信号灯控制器 | `TrafficLight` 模板 | v1-v3 | 在绿、黄、红阶段间循环，维护阶段时钟和当前灯色 |
| 车辆 | `Vehicle` 模板 | v1-v3 | 经历到达、等待、穿越、完成；只在允许条件下进入路口 |
| 计时器 | 模板内/全局 `clock` | v1-v3 | 表达灯相位、到达、穿越、等待和故障超时；基础版不要求独立 Timer 进程 |
| 路口占用状态 | 共享布尔量或同步协议 | v1-v3 | 防止车辆通行期间发生不安全的相位切换 |
| 故障注入器 | `FaultInjector` 或控制器故障分支 | v3 | 触发信号灯卡死、超时检测和恢复；不得混入正常版本原始统计 |
| 观察者 | `Observer` 模板或观察时钟 | v2-v3 | 只观测性质，不改变被测系统行为，用于时限属性 |
| 行人 | 可选模板 | 扩展项 | 只有在核心实验完成后才能增加，不能作为 v1/v2 验收前置条件 |

设计原则：独立 Timer 模板不是强制要求。若普通时钟变量足以表达约束，应避免为了“进程数量”增加无意义同步和状态空间。

## 4. 基础场景参数

| 参数 | 基线值 | 说明 |
| --- | --- | --- |
| `GREEN_DURATION` | 20 s | 绿灯持续时间 |
| `YELLOW_DURATION` | 3 s | 黄灯持续时间 |
| `RED_DURATION` | 20 s | 红灯持续时间 |
| `ARRIVAL_MIN` / `ARRIVAL_MAX` | 1 s / 5 s | 车辆从接近到进入等待区的时间范围 |
| `CROSSING_MIN` / `CROSSING_MAX` | 2 s / 3 s | 车辆穿越路口的时间范围 |
| `WAIT_BOUND` | 待 v2 评审冻结 | 时限实验的最大等待时间，不应在不同 Prompt 组间临时改变 |
| `FAULT_TIMEOUT` | 待 v3 评审冻结 | 判断信号灯卡死的阈值 |

以上数值是课程演示假设。若全组决定更改，必须对所有实验组使用同一组参数，并重新运行受影响查询。

## 5. 功能需求

| 编号 | 需求 | 验收证据 |
| --- | --- | --- |
| FR-01 | 信号灯按 `Green -> Yellow -> Red -> Green` 循环 | 模板结构、仿真轨迹 |
| FR-02 | 每次灯色切换都复位相位时钟，并更新公开灯色状态 | XML 审查、仿真状态 |
| FR-03 | 车辆按 `Approach -> Waiting -> Crossing -> Done` 演进 | 模板结构、可达性见证 |
| FR-04 | 车辆到达和穿越时间分别受基线区间约束 | 不变量、卫士、时钟复位审查 |
| FR-05 | 车辆只有在绿灯剩余时间足以完成最大穿越时才可进入路口 | 安全查询、边卫士 |
| FR-06 | 车辆离开路口后释放占用状态 | 更新语句、仿真轨迹 |
| FR-07 | v3 能触发至少一种信号灯卡死故障并表示超时检测 | 故障轨迹、v3 说明 |
| FR-08 | v3 的恢复策略必须明确：自动恢复、人工复位或永久故障三者选一 | 需求决定、故障查询 |

## 6. 形式化需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| SR-01 | 安全 | 车辆处于 `Crossing` 时信号必须为绿灯 |
| SR-02 | 安全 | 信号灯任一时刻只能处于一个灯色位置 |
| SR-03 | 安全 | 若模型扩展为多车，同一时刻最多一辆车占用冲突区域 |
| SR-04 | 安全 | 正常模型所有可达状态均不死锁 |
| RR-01 | 可达 | 至少存在一条执行使车辆到达 `Done` |
| LR-01 | 活性 | v2 需要讨论并验证“等待车辆最终完成”是否为强制性质；若模型允许无限拖延，必须记录失败原因或加入公平/紧迫机制 |
| TR-01 | 时限 | 车辆进入等待区后，在冻结的 `WAIT_BOUND` 内开始穿越或到达完成状态 |
| TR-02 | 时限 | 车辆处于 `Crossing` 的时间不超过 `CROSSING_MAX` |
| FRQ-01 | 故障 | v3 中故障被触发后，超时监测状态应可达 |
| FRQ-02 | 恢复 | 若选择可恢复策略，故障后应存在恢复到正常循环的路径 |

## 7. 模型范围

### 7.1 必做范围

- v1：正常信号灯、单车、时钟约束、无死锁、安全和可达性基础查询。
- v2：保持正常场景，整合真实 AI 错误审查、同步/共享状态修复、完整查询和时限观察机制。
- v3：在已验收的正常模型上增加卡死故障、超时检测和明确恢复语义。

### 7.2 非必做范围

- 真实交通流概率分布、车辆动力学和传感器噪声。
- 多路口联动、网络通信延迟和硬件控制器代码生成。
- 行人、对向车流、多车排队；这些只能作为核心交付完成后的扩展。
- 对真实道路安全或功能安全标准作认证性结论。

## 8. 版本验收边界

| 版本 | 必须包含 | 不得声称 |
| --- | --- | --- |
| raw | LLM 原始回复、Prompt、模型/查询原文、生成环境记录 | 不得称为人工修复版或可运行模型，除非实际检查通过 |
| v1 | 当前 G5 基础模型和已有三条通过查询 | 不得称为由某个 raw 模型修复而来，因为尚无对应证据 |
| v2 | 正常场景整合模型、G3/G4 错误闭环、G7/G8 查询与结果 | 不得包含未标识的故障注入，不得覆盖 v1 |
| v3 | 故障触发、超时、恢复/永久故障语义及正常/故障验证 | 不得把“存在恢复路径”等同于“所有路径必然恢复” |

## 9. 待全组确认的决策

1. `WAIT_BOUND` 的具体值及起算点：进入 `Waiting` 还是进入 `Approach`。
2. v3 是自动恢复、人工复位还是永久卡死；不同选择对应不同活性性质。
3. v2 是否增加第二辆车。若增加，P0/P1/P2 的原始单车实验结果仍须单独保存，不能混入同一统计总体。
4. 最终报告将“CTL”作为课程习惯称呼，还是更准确地写为“UPPAAL 支持的 TCTL/CTL 风格符号查询子集”。
